# @cue/spectacles — Snap Spectacles client

A Lens Studio Lens for Snap Spectacles that turns one **double pinch** (two
quick pinches of the same hand, from Spectacles hand tracking) into one
`InterestEvent` on the Cue API. It is the Spectacles counterpart of
`apps/mentra`: same pairing flow, same device-token credential, same "never
replay, never reveal one-sided interest" rules.

**Status: not verified on real Spectacles.** The core logic is unit-tested and
was driven against the real local Cue server (pair, poll, signal, match). The
Lens adapter (`CueLens.ts`) follows the Spectacles API docs but has not been
opened in Lens Studio or run on a device. Checklist: `docs/spectacles-check.md`.

```
GestureModule pinch-down (left/right hand)
  -> Core/double-pinch.ts      two same-hand pinches within 450 ms, confidence >= 0.5
  -> Core/encounter-context.ts only when GET /api/devices/me says encounter mode is on (fresh, < 6 s)
  -> Core/pipeline.ts          debounce 1 s, one InterestEvent with a fresh eventId
  -> Core/api-client.ts        Bearer device token, retry 5xx/network with the same eventId (3 tries, 4 s budget)
  -> Core/feedback.ts          sound + one line of text, from the wearer's own ack only
```

## Layout

| Path | Role |
|---|---|
| `lens/Assets/Scripts/Cue/CueLens.ts` | Lens Studio component. The **only** file that uses Lens APIs (GestureModule, InternetModule, persistent storage, keyboard, audio, Text) |
| `lens/Assets/Scripts/Cue/Core/` | Plain TypeScript, no Lens globals and no npm imports. Compiles in Lens Studio and in Node |
| `Core/cue-client.ts` | The whole Lens behaviour behind a `CueHost` interface (what the runtime provides) |
| `Core/config.ts` | Every constant: source/gesture names, timings, routes, storage key |
| `Core/wire.ts` | Hand-written mirror of the `@cue/contracts` shapes the Lens reads and writes (zod can't be bundled into a Lens) |
| `lens/Assets/Audio/*.wav` | The three cue sounds, generated by `pnpm tones` (same notes as the Mentra tones) |
| `test/` | Vitest. `contract-parity.test.ts` holds `Core/wire.ts` to the real zod schemas |

## How it behaves

| Wearer state | Double pinch does | Display shows |
|---|---|---|
| Not linked | Opens the system keyboard for the 6-character pairing code | "Not linked. Get a code in Cue on your phone, then double pinch to enter it" |
| Linked, encounter mode off | Nothing (dropped, never replayed) | "Linked. Turn on encounter mode in Cue" |
| Linked, encounter mode on | Sends one `spectacles_hand` / `double_pinch` signal | "Encounter on. Double pinch to signal" |
| Server unreachable / stale | Nothing | "Can't reach Cue" / "Connecting..." |

A single pinch never sends anything: it is how Spectacles users select things.
Two hands pinching at once never pair.

**The diamond.** If the **Diamond** input is set, the Lens builds a small
spinning gem mesh, places it about 3 ft (91 cm) in front of the wearer at
start, and makes it a Spectacles Interaction Kit `Interactable`. Tapping
(pinch-selecting) the diamond does exactly what a double pinch does in the
table above. Both routes go through the same encounter gate and debounce.

**The match card.** If the **Match Card** input is set (an Image, e.g.
`Assets/Images/match-card-kevin.png`, a synthetic demo card "Kevin, Sport:
Ping-pong"), it is shown for **Match Card Seconds** (default 8) in front of the
wearer whenever the match cue plays. The match cue plays in two cases:
this wearer's own signal completed the match (from the ack), or the wearer
signalled first and `GET /api/devices/me` later reports a new
`activeMatchId`. `activeMatchId` only ever names a mutual, active match the
wearer is part of, so one-sided interest is still never shown. The first
value seen after the Lens starts is a baseline and is not announced.

Feedback after a signal is one of three cues, decided by the wearer's own
ack, exactly as on Mentra: **Signal sent** (also for a duplicate), **It's a
match** (this signal completed the match), **Not sent** (any rejection or
network failure, one cue for every reason so a block is not visible). The
person who signalled first also gets the match cue and card on the Lens, from
`activeMatchId` (see above).

If the web app unlinks the device (or the token is revoked), the next poll or
submit gets 401, the Lens deletes its token and returns to "Not linked".

## Set up in Lens Studio

Needs Lens Studio 5.3+ and Spectacles OS 5.58+ (Internet Access requirement).

1. Create a new **Spectacles** project in Lens Studio.
2. Copy `lens/Assets/Scripts/Cue/`, `lens/Assets/Audio/` and
   `lens/Assets/Images/` into the project's `Assets/` folder.
3. Add a scene object with a head-locked **Text** component (the status line),
   and an **Audio** component.
4. Add `CueLens` (Script) to a scene object and set its inputs:
   - **Server Url**: the Cue web origin, e.g. `https://cue-gamma-five.vercel.app`.
     Must be `https` for a Lens you can publish; plain `http` (a laptop on the
     LAN) needs Experimental APIs and is for testing only.
   - **Status Text**, **Audio**: the components from step 3.
   - **Diamond** (optional): a scene object with a RenderMeshVisual and a
     material (e.g. a Box with a PBR material). The Lens replaces its mesh
     with the gem and adds the collider and Interactable. Needs the
     Spectacles Interaction Kit package in the project.
   - **Camera Object**: the main camera, used to place the diamond and card.
   - **Match Card** (optional): a scene object with an Image component
     showing `Assets/Images/match-card-kevin.png`.
   - **Signal Sent / Match / Not Sent Sound**: the three WAVs.
   - **Dev Pairing Code** (optional): skip the keyboard while testing in the
     Preview window. Single use; clear it before publishing.
5. In the Preview panel set **Device Type Override = Spectacles**, otherwise
   every request returns 404.
6. Push the Lens to Spectacles. In the Cue web app, open Encounter, tap "Link
   glasses", then double pinch in the Lens and type the code.

## Commands

```bash
pnpm --filter @cue/spectacles typecheck   # Core + tests (CueLens.ts is compiled by Lens Studio only)
pnpm --filter @cue/spectacles lint
pnpm --filter @cue/spectacles test
pnpm --filter @cue/spectacles tones       # regenerate lens/Assets/Audio/*.wav
```

## Server side

The source/gesture pair is registered in three places, which must agree:

- `GESTURES_BY_SOURCE.spectacles_hand = ["double_pinch"]` and `DEVICE_SOURCES`
  in `packages/contracts/src/interest.ts`;
- `sourceAllowedForAuth` in `packages/matching/src/rules.ts` (a device token may
  send `mentra_touch` or `spectacles_hand`; a web session may send neither);
- SQL `public.interest_pair_ok`, widened by
  `supabase/migrations/20261115020000_spectacles_hand_source.sql`.

Matching is unchanged: a Spectacles double pinch and the other person's Mentra
swipe, Meta tap or web button make one match like any other pair.

## Security and privacy

- The device token is stored only in the Lens's persistent storage on the
  device and is sent only as `Authorization: Bearer`. All output goes through
  `Core/logger.ts`, which redacts the token, the pairing code and any
  `Bearer ...` text; `console` is a lint error in Core.
- The token can only submit interest and read the device's own encounter state.
  It cannot read profiles, matches or chat.
- No camera, microphone or location is used. The Lens only needs hand tracking
  and Internet Access.
- A device token issued to Mentra Live could send `spectacles_hand` and vice
  versa: the server does not record which kind of glasses claimed a token. Both
  are the same user's own device credential, so this does not let anyone speak
  for someone else.
- `eventId` comes from `Math.random` (no `crypto` in the Lens runtime). It is an
  idempotency key, not a secret.
